# SDK 深度代码审查与性能压测（2026-10-19）

审查基线：`develop` 的 `418744e`，开始时工作区干净。覆盖公共入口/配置、身份与会话、启动恢复/事件门控、App/Page 生命周期、协议与属性、队列/持久化、上传/网络、平台端口、无埋点运行时及 Vue 编译插桩。本报告记录本地审查与验证结果，未进行推送或发布。

## 已复现并修复的问题

| 编号 | 优先级 | 触发与影响 | 修复与回归证据 |
|---|---|---|---|

| R3 | P2 | 多选值先完整 `join` 再截断到 100 码点；数量合法的 1000 项、每项 100 万字符会超过 JS 字符串上限，使整个自动事件被拒绝。单个长文本也先全串处理再截断 | 验证全部项类型后，仅构造最多 100 码点；按 UTF-16 下标读取码点，不创建整个中间拼接串或整段 substring。回归用例在旧代码返回 `null`，修复后接纳事件；保留整体首尾空白、内部空白、控制字符、分隔符与代理对语义 |
| R4 | P2 | 身份长度校验使用 `Array.from` 展开全部码点，明显非法的超长 `userId`/`userKey` 仍分配完整字符数组、占用主线程 | 通过 UTF-16 长度下界立即拒绝明显超长输入，其余最多检查 1001 个码点。`identity.test.ts` 的红回归在旧代码迭代 100001 次，修复后不超过预算；1000 个 emoji 边界与未配对代理项规则保持一致 |

每个问题均先以真实调用路径的回归用例复现，再修复和复审。队列、上传、存储、会话和编译器审查没有发现新的已确认缺陷，未为未经证实的假设修改行为。

## 同机性能对照

Apple M1 Pro、macOS arm64、Node v24.15.0，启用显式 GC。旧版源码由 `git archive 418744e` 复制到独立临时目录，使用相同依赖和相同微基准；修复前后分开运行，不与全量测试并行。下表为预热后 5 或 7 个样本的中位耗时。

| 场景 | 修复前 | 修复后 |
|---|---:|---:|
| 百万个 emoji 的非法身份校验，10 次 | 144.91 ms | 0.0145 ms |
| 百万个 emoji 的输入文案归一化，10 次 | 19.34 ms | 0.1915 ms |
| 100 项、每项十万个 emoji 的多选值归一化，3 次 | 39.16 ms | 0.0825 ms |
| 200 条约 4 KiB Unicode 事件入队 | 3.61 ms | 3.50 ms |
| 200 条事件分批领取 | 0.51 ms | 0.53 ms |
| 慢存储下 201 次持久化实际写入次数 | 2 | 2 |
| 同场景 GC 后额外保留堆内存 | 1.16 MB | 1.17 MB |

原始结果：`test-results/review-2026-10-19-before-comparable.json` 与 `test-results/review-2026-10-19-after-comparable.json`。报告包含完整样本中位数和样本 P95，不把少量样本当作稳定尾延迟或真机 SLA。新文案处理只构造有界输出；为保留整体 trim 语义，巨大首尾空白仍可能需要线性扫描，不能宣称所有输入都只读取 100 个字符。

## 压力与故障验证

- 常规压力门禁保留 10,000 次在线事件、20,000 次离线提交、3 个固定种子各 5000 次上传故障交错，并新增 75 轮冷启动恢复。队列已有的另 5000 次固定种子交错也继续通过。
- 扩展运行时压测完成 100,000 次在线业务事件提交，全部接纳；计入初始化、恢复同意和后台事件共接收 100,005 条。队列、在途请求和定时器最终均为空，最终持久化序号正确。
- 200,000 次离线提交中，198 条业务事件与 VISIT/PAGE 填满 200 条容量，其余 199,802 次按容量契约拒绝。重连后 4 个批次排空，最大并发 3，未额外接收重复事件。
- 扩展冷启动恢复运行 250 轮，每轮 190 次离线业务提交：累计接纳 47,750 条 CUSTOM（包括恢复标记），从持久化队列恢复 48,249 条事件，最终确认接收 48,749 条事件，1000 个请求，最大并发 3，最终序号 48,749。身份、userKey、设备标识和冷启动会话逐轮核对，最终请求和定时器为 0。
- 冷启动场景使用真实 `TrackerRuntime` 和仿真宿主的异步慢写存储端口。退出前核对内存与模拟宿主存储内容逐项一致，等待写入槽位稳定后封存旧实例；恢复后逐项核对完整原载荷，交替正序/逆序完成请求，并追加迟到失败回调。每条初始业务事件还须与原始调用的数量、属性、身份对照，恢复标记与最终总量均独立断言；不是将 SDK 的初始输出直接当作正确答案。该场景验证模拟存储端口完成后的可恢复内容，不验证真实介质或文件系统刷盘。
- 文案优化完成后，对旧/新实现运行固定种子 `0x19a02026` 的 40,560 组差分：随机文本、多选数组、Unicode 空白、ASCII 控制字符、空项、分隔符边界、补充平面字符和未配对代理项，输出全部一致。差分结果保存于 `test-results/review-2026-10-19-differential.json`。

扩展压力原始数据保存于 `test-results/review-2026-10-19-after.json`。恢复场景的耗时含逐项深比较与落盘核对；仿真传输也不含真实网络延迟，因此这些耗时不作为真实设备或网络吞吐。

## 复审与交付检查

1. 基线：类型检查通过。原有 678 项测试中 674 项在沙箱通过，4 项 HTTP 测试因回环监听 `EPERM` 失败；允许本地监听后相关 10 项链路测试全部通过，未修改功能绕开环境限制。
2. 首轮修复/复审：确认并修复授权回退、标题包装累积和身份验证开销，定向回归通过。核心与无埋点分工交叉审查，补充 20,000 次标题复用及跨页迟到探针。
3. 第二轮修复/复审：增加跨进程恢复压力；发现大多选数组导致事件被拒绝，修复后继续消除整段 substring 的跨引擎分配风险。40,560 组差分通过，扩展压力通过。
4. 对验证脚本的复审继续发现一处断言缺口：任意轮数的恢复压力可能把初始少生成或错误生成的事件当成期望载荷。新增两项故障注入，分别模拟 `track` 返回成功却漏首条事件，以及首条属性错误；旧脚本两项均错误通过，修复后都明确拒绝，并保留正常 75 轮场景。恢复标记和按参数推导的总量也独立核对。
5. 最终复审第一轮：核对所有生产改动、身份/Unicode 边界、弱引用回调关系、模拟存储及最终接收集合，未发现新的可复现问题。完整 62 个文件、694 项测试通过；行/语句覆盖率超过 98%、分支超过 92%、函数超过 99%，逐文件门槛通过。
6. 最终复审第二轮：独立重读最终生产与压力场景改动，重复差分和独立微基准，并执行完整 `release:prepare`（类型、覆盖率、构建、压缩包、隔离消费者与 demo 检查），未发现新增可复现问题。

首次将扩展压测与覆盖率并行运行时发生 CPU 争用，2 项测试超出默认 5 秒；分开运行后通过。新增的 75 轮恢复测试设置独立 30 秒预算，内部保留写入稳定步数、排空请求数和完整性断言；未降低覆盖率或放宽事件正确性断言。
